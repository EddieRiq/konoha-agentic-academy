# Konoha 4.1.0 — Supervised Technical Planning

This is the v4.1.0 release package/document. Git tag creation, push and any
GitHub Release remain separate maintainer operations and are not implied or
authorized by this document.

This is a feature release on top of v4.0.2. It adds a native
`tools/konoha_v4` supervised technical-planning mode without changing
MissionPlan authority, ExecutionState schema, plan identity, human approval
semantics, fallback semantics, or provider routing.

## Feature scope

- `konoha --plan-only`: a native `tools/konoha_v4` CLI mode that produces,
  deterministically validates, displays, and lets a human review and iterate
  on a technical MissionPlan.
- `--plan-only` and `--resume` are mutually exclusive at the argument-parser
  level; omitting both keeps the existing executable conversational runtime
  as the unchanged default.
- Every plan `--plan-only` displays has already passed the same deterministic
  `hokage.validate_plan()` checks required in normal mode: governance,
  workspace policy, budget arithmetic, gate/family/model eligibility, and
  (for v4.0.1-format plans) the structured `mission_constraints` manifest's
  shape, source-text provenance and match against the plan.
- Human review supports an explicit affirmative, an explicit rejection, or
  free-form requested changes, using the exact same input protocol as normal
  mode.
- A requested change is confirmed back to the human before anything happens;
  once confirmed, it is recorded as human continuity evidence via the
  existing `MissionContinuityStore.record_requested_change()`, and Codex is
  invoked again for a corrected, re-validated plan.
- The reviewed technical MissionPlan is returned to the human without
  execution authority.

## Safety and authority

- Codex planning output is proposal/evidence only, exactly as in normal mode;
  it carries no authority of its own.
- Human acceptance in `--plan-only` mode means acceptance of the reviewed
  technical planning artifact only — it does not mean execution approval.
- `MissionPlan.approval` remains `status="pending"`, `approved_by=None`,
  `approved_at=None` after `--plan-only` acceptance.
- Continuity execution approval remains ungranted:
  `MissionContinuityStore.record_approval("approved", ...)` is never called
  in `--plan-only` mode.
- No `AssignmentApproval` is created or consumed.
- The canonical executable persisted-plan surface, `plan.json`, is never
  written in `--plan-only` mode.
- `execution_state.json` is never created, since it is only ever written
  from inside the execution path that `--plan-only` never reaches.
- `execute_or_resume_plan()` / `_run_resumable_execution()` and any provider
  invocation for any assignment are never reached in `--plan-only` mode.
- The normal execution approval path in the default conversational mode is
  unchanged.
- No `MissionPlan` or `ExecutionState` schema changes were introduced;
  `plan_hash` and `plan_identity` are unchanged.

## Compatibility

- v4.0.0 and v4.0.1 persisted-plan compatibility is unchanged; `--plan-only`
  never loads a persisted plan and only ever works with in-memory plans
  freshly produced by `build_plan()`.
- v4.0.2 pre-invocation provider/model readiness behavior is unchanged; it
  is simply never reached in `--plan-only` mode, since there is nothing
  pending to invoke.

## Known limitations

- A plan reviewed and accepted through `--plan-only` is not resumable
  through `konoha --resume <mission_id>` in this release, since no
  `plan.json` is ever written for it.
- There is no promotion path from a plan-only artifact into an executable,
  persisted mission in v4.1.0.
- `run_technical_plan` in `tools/hokage_orchestrator` remains registered and
  provider-routed but has no orchestrator implementation and fails closed;
  `--plan-only` does not call, bridge, wrap, or otherwise implement it.
- Automatic provider/family fallback is still not implemented; `fallback`
  remains declarative-only data on `AgentAssignment`.
- Codex/Claude readiness limitations from v4.0.2 remain: readiness does not
  deterministically prove authentication or that an arbitrary approved model
  name is currently available.
- Cross-session repository Git `HEAD`/worktree drift remains unresolved.
- Provider/model output remains evidence only and does not grant authority.
