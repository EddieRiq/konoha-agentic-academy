# Konoha 4.0.2 — Runtime Continuity & Provider Integrity

This is the v4.0.2 release package/document. Git tag creation, push and any
GitHub Release remain separate maintainer operations and are not implied or
authorized by this document.

This is a patch/hardening release on top of v4.0.1. It closes the
approval-time-to-execution provider-readiness gap without changing
MissionPlan authority, ExecutionState schema, plan identity, human approval
semantics, fallback semantics, or provider routing.

## Patch scope

- Every pending assignment receives a fresh deterministic readiness probe for
  its exact approved provider immediately before invocation.
- The readiness gate runs after existing plan identity, assignment gate,
  human approval and family validation, but before Git execution-baseline
  capture, `executing` persistence and provider invocation.
- Codex and Claude use the existing deterministic provider-level probe:
  executable presence plus successful `--version`.
- Ollama additionally requires the exact approved assignment model to appear
  verbatim in the freshly-probed local model inventory.
- Readiness failures return stable machine-readable diagnostics:
  `provider_not_ready:<provider>` or
  `model_not_ready:ollama/<model>`.
- A readiness failure leaves MissionPlan, ExecutionState, assignment evidence
  and approval-authority state unchanged.
- A valid `separate_human_approval` is not consumed by a readiness failure and
  can authorize the same unchanged assignment after the environment becomes
  ready.
- Conversational execution pauses after the first readiness failure instead of
  automatically polling or retrying.
- Multiple assignments executed within one process are independently
  re-probed, so provider readiness is not trusted from an earlier assignment.
- v4.0.0 legacy plans without a `mission_constraints` field and v4.0.1 plans
  with the structured manifest remain compatible.

## Safety and authority

Fresh provider readiness is operational evidence only. It is never persisted
as human authority and never changes the approved provider, model, family,
execution gate or fallback policy.

This patch adds no automatic fallback, provider/model substitution, retry,
background polling, model download, network authority or new execution
authority.

Provider executable path and CLI version are operational evidence rather than
persisted mission authority; an ordinary provider CLI upgrade does not by
itself invalidate an approved mission.

## Known limitations

- Codex/Claude readiness does not deterministically prove authentication.
- Codex/Claude readiness does not deterministically prove that an arbitrary
  approved model name is currently available.
- Authentication or other provider failures not detectable by the readiness
  probe may still surface during invocation.
- Cross-session repository Git `HEAD` drift remains unresolved.
- Cross-session working-tree drift remains unresolved outside the existing
  per-invocation mutation checks.
- `fallback` remains declarative only; automatic provider/family failover is
  not implemented.
- `run_technical_plan` remains registered and provider-routed but has no
  orchestrator implementation and fails closed.
- Provider/model output remains evidence only and does not grant authority.
