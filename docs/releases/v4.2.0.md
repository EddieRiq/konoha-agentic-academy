# Konoha 4.2.0 — Repository Comprehension, Supervised Learning and Conversational Integration

This is the v4.2.0 release package/document. Git tag creation, push and any
GitHub Release remain separate maintainer operations and are not implied or
authorized by this document.

This is one integrated minor release on top of v4.1.1. The internal
v4.2.0/v4.2.1 engineering package labels and the C1/C2A/C2B/C3 gates used
during development were never separate releases; their content ships here
together with the final conversational CLI integration.

## Scope

### Repository comprehension and exact evidence

- Every canonical required source is materialized with explicit bounds. One
  resolution mapping is retained for both the executor gate and the worker's
  `resolved_source_bundle`; sources are not resolved again for the prompt.
- The exact original human request is loaded from durable
  `continuity.original_request`. Raw dependency output is no longer copied
  into worker prompts. Missing material pauses before invocation without
  consuming approval or fabricating provider evidence.
- Plans bind the exact persisted RepositoryEvidencePack (`pack_id`) and the
  SHA-256 of its complete payload before approval. Execution and resume
  reload that exact pack, verify integrity and root identity, and check
  currentness. Missing, corrupt or stale packs stop before provider
  readiness, Git baseline, executing state or invocation; they are never
  silently refreshed.
- Generic, evidence-linked repository studies (components, relationships,
  capabilities, tests, documentation statements, candidates) with exact
  locators, plus a local terminal workflow
  (`python -m tools.repo_evidence.workflow`).
- Evidence reads refuse file aliases into excluded content and use
  descriptor-relative reads; tracked-deletion fingerprints and the
  failure-log boundary are preserved.

### Human repository teachback

- The canonical teachback engine gains a repository comprehension loop.
  Only the exact single human line `:entendido` closes it; case or spacing
  variants, ordinary “yes”, and model output do not.
- Repository understanding is separate from execution approval, mission
  teachback and mission closure.

### Supervised recommendations and public-repository learning

- Proposal-only self-improvement recommendations built from retained
  evidence, separating deterministic `validated` candidates, locator-linked
  `model_suggestions` and `suppressed` items, reusing the local-model audit
  approach.
- Donor learning compares an explicitly authorized local public checkout
  with Konoha after human teachback of both, preserving provenance on both
  sides and recording compatibility, licensing and scope concerns.

### Conversational CLI integration

- `konoha` routes `understand this repository`, `explain …`, `show me the
  evidence`, `what could Konoha improve?`, donor comparison and `:repo …`
  commands (`help`, `study`, `authorize`, `cancel`, `list`, `resume`,
  `recommend`, `compare`, `details`, `leave`) through the same study and
  teachback APIs. No parallel study engine or memory index is created.
- Study state stays private under `KONOHA_STATE_ROOT/repository-studies`.
- `implement recommendation NUMBER` enters the existing supervised mission
  planning flow; the exact human request remains the authority input and the
  recommendation is evidence-only context.

## Safety and authority

- Repository conversation routes do not probe or invoke providers, execute
  tests or application code, or patch files. Provider readiness and mission
  planning begin only on a mission turn.
- External checkouts require a fresh exact `:repo authorize <challenge>`
  command. Naming a path, calling it “authorized”, or answering `yes` grants
  nothing. Private/excluded roots are refused. `--public` is the human's
  assertion, not a remote visibility check.
- No clone, fetch or download occurs. Acquisition from real remotes remains a
  separate explicit human/network authorization boundary.
- Recommendations remain `proposed` with `authorizes_action=false`. Donor
  adoption is proposal-only: donor code is never copied or adopted by study,
  and any implementation requires a separately approved mission with its
  existing approval, review, teachback and closure gates.
- No automatic provider/family fallback was added.

## Compatibility

- The MissionPlan schema adds a nullable `repository_evidence` binding
  (`pack_id`, `sha256`). Persisted plans that omit it still load; when it is
  absent, the canonical payload, `plan_hash` and `plan_identity` are computed
  as before.
- New schemas under `schemas/runtime/`: `repository_study_record`,
  `repository_teachback`, `self_improvement_recommendations` and
  `donor_learning_recommendations`.
- Legacy plans that need repository evidence must be replanned: an absent
  binding cannot authorize acquisition, and changed repository content
  requires a new planning transaction or a new study with its own teachback.
- `--plan-only` and `--resume` semantics are unchanged; `--plan-only`
  continues to permit planning/review acceptance only.

## Verification

- Deterministic regression coverage was added for required-source
  materialization, approved repository evidence, repository studies and
  teachback, recommendations, public schema contracts, and conversational
  repository journeys.
- This document does not record test or live smoke results. Verification
  evidence for the release commit belongs to the separate review and
  release gates.

## Known limitations

- Evidence extraction is static and bounded (per-file, per-list and
  per-category limits) and primarily Python-oriented. Test discovery does not
  prove execution or coverage; documentation statements are claims.
- An empty recommendation result does not prove that no improvements exist,
  and an unused-symbol candidate is not proof that deletion is safe.
- Local study state integrity checks detect mismatches with the approved
  reference; they are not authentication against an owner rewriting every
  local record.
- A provider may return schema-valid but semantically weak evidence.
  Provider output remains evidence only, and independent review may still
  block the mission; this is not fixed in v4.2.0.
- Known limitations carried over from v4.1.1 (see
  `docs/releases/v4.1.1.md`) remain unresolved, including no automatic
  provider/family fallback.
