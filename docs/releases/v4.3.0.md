# Konoha v4.3.0 — Interactive Shell Foundation

## Objective

Introduce a normal human-TTY terminal entry over the stable Konoha Core while
preserving explicit CLI and script surfaces and the existing supervised
authority model.

## User-visible capability

Running `konoha` in a human TTY opens the Interactive Shell; `konoha shell`
remains an explicit entry. Natural-language input routes into existing
supervised flows. Single-line colon controls provide shell help, status,
repository study, mission guidance, review guidance, provider executable
presence, local workspace status, Git metadata, and clean exit. The exact
controls are documented in the [operator guide](../guides/konoha_interactive_shell.md).

## Project and workspace boundary

Startup reads safe Git metadata and sanitizes values displayed in the
terminal. It does not inspect repository files, mission state, or provider
readiness. Project detection does not grant repository inspection, model
invocation, or mutation permission. Project-scoped local state uses XDG or the
user's local state directory outside the repository by default; the
`KONOHA_PROJECT_STATE_ROOT` and `KONOHA_STATE_ROOT` variables can override the
location. First creation requires explicit confirmation.

## Visual identity and local art

The shell displays the Konoha wordmark and original generic text mascots.
Operators may set `KONOHA_ART_DIR` to use their own local artwork. If `chafa`
is already installed, Konoha can use it to render eligible local images. Konoha
does not install `chafa` or download artwork. No copyrighted franchise art is
shipped.

## Compatibility

Non-TTY invocations keep the existing CLI conversation behavior. Explicit CLI
and script interfaces remain available. Colon commands are shell controls only;
legacy conversation framing remains compatible. The release contract aligns
package/runtime and CLI version `4.3.0`, runtime tag `v4.3.0`, and installer
default tag `v4.3.0`.

## Authority and safety

Natural language expresses intent and does not approve a plan or action.
Startup does not invoke a provider. No Web UI, daemon, or background autonomy
is introduced. Review, Teachback, execution, Git, and release gates retain
their existing authority boundaries.

## Validation

Canonical full discovery passed 58/58 suites and 1,266 tests. The established
15-suite release regression passed 15/15 suites and 852 tests. Both runs had
zero failures, errors, skips, and timeouts. The version contract, CLI version,
local clean-install smoke, explicit shell exit smoke, and `git diff --check`
also passed.

## Known limitations

The review control is informational and does not expose review state. Provider
status reports executable presence only. Local artwork is optional and depends
on the operator's own files and an already installed `chafa`. The shell is a
terminal presentation and routing layer.

This release does not include Munder Diffing, social posting, streaming bots,
video clipping, Graphify, project learning, or autonomous agents. The media
scenario is dogfood evidence only.
