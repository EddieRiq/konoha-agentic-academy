# Konoha 4.0.1 — Mission Integrity Hardening

This is the v4.0.1 release package/document. Git tag creation, push and any
GitHub Release remain separate maintainer operations and are not implied or
authorized by this document.

This is a patch/hardening release on top of v4.0.0: it adds deterministic
structural verification of mission constraints without changing fallback
runtime semantics, ExecutionState, approval command semantics, or provider
invocation behavior.

## Patch scope

- New provider-generated MissionPlans include a structured
  `mission_constraints` manifest alongside `explicit_facts`.
- Supported structural constraints are validated deterministically against
  the generated MissionPlan before human approval and before execution.
- Every constraint's `source_text` must occur verbatim as a substring of
  authorized human mission/change text; no normalization, semantic
  matching, or paraphrase matching is performed.
- Assignment-position constraints (selected by position in
  `plan.assignments`, not by model-generated `task_id`) can bind provider,
  family, model, network/mutation/private_context flags, execution_gate,
  fallback, token estimates and dependencies.
- Plan-scope constraints deterministically check assignment count, the
  maximum total token ceiling and the replanning reserve.
- `approval_summary` exposes the structured manifest — target, operator,
  value and exact source text — to the human before approval.
- `mission_constraints=None` remains the explicit legacy v4.0.0
  compatibility shape.
- A legacy persisted plan (no `mission_constraints` field) reloads with
  `mission_constraints=None` and retains its pre-v4.0.1 `plan_hash` and
  `plan_identity` exactly.
- Automatic deterministic validator feedback used during corrective
  replanning is never promoted to human authority for constraint
  provenance; only the original mission text and confirmed human
  requested-change text qualify.

## Known limitations

- Extraction completeness from arbitrary natural language is NOT
  deterministically guaranteed; the human still reviews whether the
  extraction captured every intended constraint.
- `mission_constraints` only covers the supported structural subset
  described above; `explicit_facts` remains the general textual evidence
  surface for mission facts and constraints.
- `fallback` remains declarative only; automatic provider/family failover
  is not implemented.
- `run_technical_plan` remains registered and provider-routed, but has no
  orchestrator implementation yet; it fails closed rather than executing.
- Model/planner output, including `mission_constraints`, remains
  proposal/evidence only, subject to deterministic validation and explicit
  human approval.
